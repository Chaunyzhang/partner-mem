# Partner-Mem V1 产品需求文档

> 本文是 Partner-Mem V1 的正式产品定义。研究文档提供产品证据，正式需求以本文记录的已确认决策为准。

## 0. 项目创建方式

Partner-Mem V1 按从零到一的方式创建。产品由 Harness 适配插件、Partner-Mem 内核、持久存储、可重建索引和模型可见检索 Tool 共同组成；各部分按照本 PRD 的产品规则设计和实现。

## 1. 产品定位

Partner-Mem 是由不同 Harness 的适配插件接入的原文消息永久存储、宿主结构字段管理与检索内核。本 PRD 定义其数据边界、写入条件与检索行为。

### 1.1 明确不做的事

1. Partner-Mem 永久保存所有已写入的轮次节点、节点内完整原文及其宿主结构字段；不因时间流逝、会话结束或上下文压缩而自动过期、汇总或丢弃。
2. Partner-Mem 不建设“长期记忆对象”：不把原文沉淀为用户画像、偏好、长期事实或其他可持续演化的对象。
3. 除将同一宿主轮次中可明确关联的问题文字与回答文字结构化归入同一轮次节点，并根据适配插件提供的来源信息生成或解析宿主结构字段外，Partner-Mem 不做任何记忆加工：不总结、不压缩、不合并不同轮次节点，也不从正文提取持久字段、事实或状态。
4. V1 不定义或提取任何正文派生字段，包括主题、实体、偏好、意图、任务、更新状态、事件时间、摘要或因果关系。

## 2. 已确认的产品决策

### 2.1 对话边界

1. 普通检索的对话范围由 Partner-Mem 生成并维护的稳定 `harness_id + conversation_id` 共同定义。
2. `harness_id` 标识一个具体的 Harness 实例、租户或配置隔离单元，不只表示 Harness 产品名称；不同实例必须具有不同的 `harness_id`。
3. Harness 产品类型作为可重复的 `harness_type` 字段记录，例如 Hermes 或 OpenClaw；多个不同 `harness_id` 可以具有相同的 `harness_type`。
4. 适配插件首次注册该 Harness 实例时，由 Partner-Mem 生成全局唯一的 `harness_id`；适配插件必须持久保存该标识，并确保插件进程重启、Harness 重启和普通版本升级后该 ID 保持不变。
5. 轮次节点中正式保存的 `conversation_id`、`thread_id`、`message_id`、`author_id`、`agent_id` 等对象标识均由 Partner-Mem 生成，并在整个 Partner-Mem 范围内全局唯一。相同对象始终映射到同一 ID；不同对象即使来自不同 Harness，也不得使用相同 ID。
6. 适配插件只向 Partner-Mem 提供从 Harness 生命周期取得的来源对象标识。Partner-Mem 持久维护“来源 Harness 对象 → Partner-Mem 正式 ID”的映射；同一来源对象再次出现时必须解析到原正式 ID，不同 Harness 中相同的原始标识必须解析为不同的正式 ID。Harness 原始标识不得直接充当轮次节点中的正式对象 ID。
7. Partner-Mem 不根据文本相似度、主题相似度或其他语义信号，推断、合并或自动跨越对话边界。
8. 同一 Harness 实例创建新聊天时，适配插件应提供该聊天的来源对象标识，由 Partner-Mem 创建新的全局唯一 `conversation_id`；即使话题相同，也不自动带入其他对话的记忆。
9. 用户回到同一 Harness 实例的同一聊天继续对话时，适配插件应继续提供同一来源对象标识，由 Partner-Mem 解析回原 `harness_id + conversation_id`。
10. 在当前 `harness_id + conversation_id` 范围内没有命中时，Partner-Mem 返回空证据；不得从其他对话或其他 Harness 补充猜测性证据。
11. 普通关键词与向量检索默认只查询当前 `harness_id + conversation_id`；只有 Harness 中的 Agent 在 Tool 调用中明确选择已确认的当前 Agent 历史范围时，才查询当前 Harness 实例中该 Agent 可访问的历史 conversations。V1 不支持其他自动跨对话或跨 Harness 扩展。

### 2.2 最终可见消息的写入时机

1. Partner-Mem 只接收适配插件从 Harness 生命周期中捕获的、已经最终显示给用户的完整消息正文。
2. 对用户消息，适配插件在确认其已经最终显示后提交写入。
3. 对助手消息，适配插件必须在生成完成且最终内容确实显示成功后，再提交一次完整正文。
4. Partner-Mem 不接收或存储以下内容：
   - 流式输出中的片段；
   - 尚未完成的生成草稿；
   - 工具调用过程；
   - 内部推理；
   - 生成失败、取消或未最终显示给用户的内容。
5. 适配插件向 Partner-Mem 提交的消息始终是完整、最终可见的正文；不得将同一条最终消息拆成多个流式片段提交。
6. Partner-Mem 对提交失败或原文写入失败不提供兜底、自动重试或补写；只有成功写入的原文才视为已经记录，未成功写入的原文不进入记录。
7. 完整文字原文一旦成功写入，对应轮次节点即视为已经记录；V1 没有正文派生字段提取、重提取或相关重试流程。
8. 写入动作及其结果由适配插件与 Partner-Mem 内部处理；Harness 的正常对话流程不调用 Partner-Mem 写入接口，也不接收写入成功状态或 `node_id`。
9. 原文写入在后台异步进行，不得阻塞、中断或改变 Harness 的正常对话。Partner-Mem 的延迟、不可用或处理失败不得改变用户已经看到的消息，也不得要求 Harness 或用户重试。
10. V1 只记录用户问题和助手回答中最终可见的文字正文；不保存图片、文件、音频、视频或其他附件内容，也不保存消息内容形式字段。包含附件的消息若同时具有最终可见文字，只写入其中的文字正文。

### 2.3 轮次节点是基本单位

1. 一个宿主对话轮次中成功写入的最终可见文字构成一个轮次节点。节点最多包含一个问题文字和一个回答文字，也可以只包含其中一侧；问题和回答都没有成功写入的文字时，不创建节点。
2. 创建任何轮次节点都必须由 Partner-Mem 成功解析出有效的 `harness_id` 和全局唯一的 `conversation_id`，并具有至少一侧成功写入的文字正文；任一必填条件缺失时，本次节点写入失败。`thread_id`、`message_id`、显示时间、`author_id`、`agent_id` 等其他字段缺失时，原文仍可保存，相应字段为空。
3. 轮次节点是 Partner-Mem 永久保存、宿主结构字段管理和检索的基本单位。
4. 节点必须完整保留实际写入的问题文字、回答文字及其各自角色；缺失的一侧保持为空，不得生成占位文本、OCR、附件描述或其他内容补齐。
5. Agent 产品中的修改、补充、纠正、重发或重新请求通过新的用户消息发起，并与其后的助手回答构成新的轮次节点；此前轮次节点的原文保持不变，不得把新消息作为同一轮次节点中的回答版本或原地修改。
6. 将一个问题及其回答归入同一节点是结构化分组，不表示系统从中合成新的事实、摘要、偏好或其他长期记忆对象。

### 2.4 轮次节点的创建与补充

1. 用户问题具有最终可见文字且该文字成功写入时，Partner-Mem 创建轮次节点，生成全局唯一的 `node_id`，保存完整问题文字，并根据适配插件提供的来源信息生成或解析问题侧正式字段。
2. 用户消息不含文字时，Partner-Mem 不创建空问题节点，也不根据附件生成替代文字；适配插件可以在当前运行期保留该宿主 turn 的临时上下文，等待是否出现最终可见回答文字。
3. 助手回答具有最终可见文字时：若适配插件持有同一宿主 turn 对应的 `node_id`，Partner-Mem 将完整回答文字及根据来源信息生成或解析的回答侧正式字段补入该节点；若运行期 `node_id` 映射已经丢失，但适配插件提供的来源消息标识能够通过 Partner-Mem 的持久对象映射唯一解析到一个已有轮次节点，也可以补入该节点。若适配插件能够明确确认该 turn 从未创建过问题侧节点，则 Partner-Mem 可以创建一个只包含该回答的轮次节点并生成新的全局唯一 `node_id`，同时根据适配插件从该 turn 获取的来源信息生成或解析回答侧正式字段。Agent 主动发送、没有对应用户问题的最终可见文字，也按只有回答侧的轮次节点保存。一个轮次节点已经保存回答后，不得再追加或覆盖第二个回答；新的用户消息及其回答必须创建新的轮次节点。不得根据正文、时间邻近或其他语义信号寻找问题节点代替。
4. `node_id` 只在 Partner-Mem 与适配插件之间使用，Harness 无需获取或管理。不同轮次节点的 `node_id` 不得相同。
5. 适配插件只在当前运行期内保存宿主 turn 与 `node_id` 的临时映射；该临时映射本身不作为长期图数据保存。插件重启或临时映射丢失后，Partner-Mem 只允许通过适配插件提供的来源消息标识及其持久对象映射精确恢复原节点；无法唯一解析且无法明确排除该 turn 已存在问题侧节点时，不得猜测配对，也不得另建回答侧节点。同一宿主 turn 最多对应一个持久轮次节点。重复提交不设置单独状态或处理分支，仍按来源对象映射、单轮次单节点和已写入原文不覆盖的规则执行。
6. 问题和回答分别保存 `question_role`、`question_author_id`、`answer_role` 与 `answer_author_id`；回答另存实际生成该回答的 `answer_agent_id`。角色按适配插件从 Harness 获取的来源信息保存；作者与 Agent 的正式 ID 由 Partner-Mem 根据来源对象生成或解析。这些字段的保存不以对应一侧存在文字为前提；没有可用来源信息时相应字段才为空。不得根据正文猜测。相同作者或 Agent 始终映射到同一正式 ID。
7. 适配插件提供来源消息标识时，由 Partner-Mem 生成或解析全局唯一的 `question_message_id` 与 `answer_message_id`。消息 ID 的保存不以对应一侧存在文字为前提，没有可用来源标识时才为空。消息 ID 缺失不影响文字原文写入。即使消息 ID 已保存，只有该 ID 对应消息的文字原文也已保存时，它才能作为持久显式回复边的端点。消息 ID 只作为所属轮次节点的字段保存，不创建独立图节点。
8. 轮次节点分别保存适配插件从 Harness 获取的 `question_visible_at` 与 `answer_visible_at`。显示时间的保存不以对应一侧存在文字为前提，宿主未提供时相应字段为空。不得用 Partner-Mem 的后台写入时间代替宿主显示时间。后台写入时间可以作为内部运行信息，但不得用于忠实重组宿主对话。
9. 只有问题文字的节点永久保留问题原文；只有回答文字的节点永久保留回答原文。任一侧缺失都不表示 Partner-Mem 判断了生成失败、取消或其他宿主状态。
10. V1 不同步宿主对已写入消息的原地编辑或撤回，也不得据此修改或删除已写入原文。修改、补充和纠正必须以新的独立消息和轮次节点写入，此前节点永久保留。

### 2.5 V1 节点字段与内容索引

1. V1 的持久节点字段只包括 Partner-Mem 生成的正式对象 ID，以及适配插件从 Harness 生命周期提供来源信息的宿主结构字段，例如 conversation、thread、message、Harness 类型、Agent、作者/角色和消息显示时间。
2. V1 不从问题或回答正文提取任何持久字段，也不执行正文分类、字段重提取、抽取版本管理或字段级重试。
3. 完整文字原文是内容检索的唯一材料。Partner-Mem 为完整原文建立可重建的全文/BM25 索引和语义向量索引；这些索引只用于内部产生查询候选，不是节点字段、图边、事实或回答证据。模型可见检索 Tool 必须把最终命中解析回完整轮次原文后再返回。
4. 宿主结构字段只属于其轮次节点，不创建 conversation、thread、Harness、Agent、作者等独立图节点，也不建立 `IN_CONVERSATION`、`IN_THREAD` 等归属边。
5. 相同宿主字段值只用于查询期筛选、分组、排序或重组完整原文节点，不因此形成持久边。
6. 节点实际包含问题文字、回答文字或两者，可直接根据对应原文字段是否为空判断；V1 不另设轮次完成状态、消息内容形式字段或统一的“最终可见”状态。
7. 宿主结构字段的生成、解析或缺失不得改写、压缩或影响轮次节点中的完整原文。
8. 跨节点关联只服务于找回完整原文证据；不得合并、改写节点原文或据此生成新的事实、摘要、偏好或状态。

### 2.6 图结构、时间与会话片段重组

1. Partner-Mem 的图不是线性时间线；系统不得给节点分配人为编号或“图中位置”，也不得将“下一条消息”作为 V1 必需的持久图边。
2. 节点在一次检索中的可达范围，由节点字段属性和适配插件从 Harness 获取的明确节点间关系决定。属性包括会话、时间、thread、角色、Agent、Harness 等；相同字段值用于查询期筛选、分组或候选扩展，不因此形成持久边。明确节点间关系包括宿主提供的显式回复关系。
3. Partner-Mem 不因命中一个节点而自动追加时间邻近节点。Harness 可以使用 Tool 已返回节点中的 `harness_id`、`conversation_id`、宿主显示时间与显示顺序，按宿主规则组织或展示这些已返回的完整原文；该展示重组不产生新节点、新事实或新的长期记忆。
4. 宿主若提供显示顺序，该信息仅用于忠实还原宿主展示；它不是节点的空间位置，也不是 V1 必需的图字段或持久图边。
5. 本次查询选择的时间范围、会话片段、候选子图、语义近似、路径权重、相关度和排序均属于查询工作数据；查询结束后不作为长期图数据保存。
6. V1 只有适配插件从 Harness 获取的、两个原文节点之间的显式回复关系可以持续保存为证据关系。Partner-Mem 必须根据适配插件提供的两端来源消息标识，解析出对应的正式 `message_id` 与已保存轮次节点，并确认两端各自被回复或发起回复的消息文字原文已经保存；任一端无法解析或缺少对应文字原文时，不得创建该边。关系两端必须分别回到各自完整原文，且不得被提升为脱离原文的全局事实或当前真值。问题及其回答归入同一轮次节点不是节点间边；conversation、thread、Harness、Agent 等归属只通过节点字段表达。V1 不持久保存任何根据正文推断出的跨节点关系。
7. 每条持久显式回复边必须同时保存发起回复与被回复两端的 `node_id` 和 Partner-Mem 正式 `message_id`，以明确关系实际发生在哪两条消息之间；不得只记录两个轮次节点而丢失具体消息端点。边上的消息 ID 仅作为来源锚点，不创建独立消息节点。

### 2.7 检索 Tool 的划分与原文返回

1. 提供给 Harness 中 Agent 的检索 Tool 按其检索对象和索引形态划分，例如完整原文倒排索引上的关键词检索、向量索引上的语义检索，以及持久节点和关系边上的图跳转；不得按“先搜索候选、再召回证据”等需求处理阶段拆分 Tool。
2. 每个模型可见检索 Tool 可以在 Partner-Mem 内部产生、排序和去重候选，但返回给 Harness 时必须已经解析为命中轮次节点的完整问题与回答原文，并携带对应正式 `node_id` 和宿主结构字段。节点只有一侧文字时，如实返回该侧原文，另一侧为空。
3. 模型不得为了取得命中节点的原文而再调用第二个读取 Tool。按正式 `node_id` 精确读取完整轮次节点的 `get_node` 能力只作为 Harness 适配插件与 Partner-Mem 内核之间的内部接口，不注册为 Agent 可见 Tool。
4. 关键词、向量和图检索的内部评分、路径和候选记录不是回答证据；Tool 返回的完整轮次原文才是 Harness 用于回答的证据。
5. 关键词检索与向量检索共用两档查询范围：默认的当前对话范围只查询适配插件注入的当前 `harness_id + conversation_id`；当前 Agent 历史范围查询当前 Harness 实例中适配插件注入的当前 `agent_id` 可访问的历史 conversations。模型只能选择范围名称，不得提交或覆盖正式 `harness_id`、`conversation_id` 或 `agent_id`。
6. 图跳转从已知正式 `node_id` 出发，不使用上述范围选择起点；但每次读取起点、边和目标节点时都必须执行相同的 Harness 与 Agent 访问边界校验，不得借图关系跨越无权访问的节点。
7. 图跳转 Tool 的一次调用支持由调用方选择 1 至 3 跳，最大深度硬限制为 3。Tool 内部负责逐层遍历、循环检测、节点去重和保留到达每个结果节点的实际持久关系路径；不得越过不存在、未持久保存、关系类型不允许或访问边界校验失败的边。所有返回节点仍须包含完整轮次原文。
8. 向量索引对每个轮次节点最多建立一个向量：节点同时有问题和回答文字时，按固定的“问题原文在前、回答原文在后”顺序拼接后生成向量；只有一侧文字时，仅使用存在的一侧。该向量直接回指正式 `node_id`，V1 不为问题侧和回答侧分别建立向量条目。
9. V1 不提供同时包办关键词与向量召回的模型可见混合检索 Tool，也不在 Partner-Mem 内核对两者执行统一分数、RRF 或其他跨 Tool 排序。Harness 中的 Agent 需要两种检索时分别调用对应 Tool，并根据返回结果共有的正式 `node_id` 识别重复轮次；本次组合和选择只属于 Harness 的查询期工作，不持久化。
10. 图跳转 Tool 每次调用只接受一个正式起点 `node_id`。调用方必须选择 `parent`、`replies` 或 `both` 方向；`max_depth` 允许 1 至 3，默认 1；返回节点总数 `limit` 默认 10、最大 20。Tool 按广度优先顺序遍历，先返回较近跳数；同一跳数内优先按宿主显示顺序排列，宿主未提供时按消息显示时间排列，仍相同时按 `node_id` 稳定排序。达到总数上限时必须返回 `truncated: true`。每个结果都须包含从起点到该节点的实际持久关系路径和完整轮次原文；遇到无权节点、无效关系或循环时停止对应分支。
11. V1 只向 Harness 中的 Agent 注册三个检索 Tool：`partner_mem_keyword_search`、`partner_mem_vector_search` 和 `partner_mem_graph_traverse`。`get_node`、运行状态检查和索引管理均不注册为模型可见 Tool。
12. `partner_mem_keyword_search` 的模型输入仅包括必填非空字符串 `query`、可选 `scope` 和可选 `limit`。`scope` 使用第 5 条确认的两档范围并默认当前 conversation；`limit` 默认 10、最大 20。Tool 使用全文/BM25 索引排序并直接返回完整轮次原文。
13. `partner_mem_vector_search` 与关键词 Tool 使用相同的 `query`、`scope` 和 `limit` 输入契约；查询向量由 Partner-Mem 内部从 `query` 生成，模型不得提交向量、模型名称或相似度阈值。Tool 按向量近邻排序并直接返回完整轮次原文。
14. `partner_mem_graph_traverse` 的模型输入仅包括必填 `start_node_id`、必填 `direction`，以及可选 `max_depth` 和 `limit`；不接受自然语言 `query`、`scope` 或 `edge_type`。V1 只有一种允许跳转的显式回复关系，调用方无需选择边类型。
15. 三个 Tool 共用结构化输出外壳：`status`、`retrieval_type`、`truncated` 和 `evidence_items[]`。每个 evidence item 包含从 1 开始的 `rank`、正式 `node_id`、Harness/conversation/thread 等宿主结构字段，以及完整 `question` 和 `answer` 原文对象；图跳转结果另在对应 item 中携带实际持久关系路径。内部 BM25 分数、向量相似度和跨 Tool 可比分数不返回为证据。
16. 成功但没有命中时返回 `status: empty` 和空 `evidence_items[]`；Partner-Mem 不可用时返回 `status: error`、稳定错误码和空 `evidence_items[]`。任一检索 Tool 失败都不得阻塞、终止或改变 Harness 的正常对话流程，Agent 不得把空结果或错误编造成历史证据。

## 3. V1 闭环状态

上述写入、节点、关系、索引与检索 Tool 产品规则已确认。具体数据库、全文 tokenizer、embedding model、向量库和进程通信方式通过独立工程选型确定，并满足本 PRD 已确认的原文证据、身份边界、Tool 划分和失败语义。
